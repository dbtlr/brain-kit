# Partner model schema

The partner model is a two-layer system: a **JSONL observation log** that grows over time, and a **consolidated markdown model** that summarizes what the log has learned. Skills write to the log; consolidation rewrites the model from the log.

---

## JSONL log entry schema

Each entry in the log is one JSON object on its own line. The log file is append-only — entries are never modified or deleted.

```jsonl
{"ts": "2026-04-11T22:00:00Z", "session": "brain-kit-pr1", "project": "brain-kit", "type": "observation", "pattern_ref": null, "text": "Prefers to read source material before starting implementation work."}
```

### Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `ts` | string (ISO 8601) | yes | Timestamp of the observation. Use UTC. |
| `session` | string | yes | Human-readable session identifier. Convention: `{project}-{what-happened}`, e.g., `brain-kit-pr1` or `norn-cleanup`. |
| `project` | string | yes | Which project the observation came from. Always required — observations without project context are ambiguous. |
| `type` | string | yes | Entry type. One of: `observation`, `confirmation`, `correction`, `calibration`. |
| `pattern_ref` | string or null | yes | Short string referencing an existing pattern being confirmed or corrected. Null for new observations. |
| `text` | string | yes | The observation itself. One sentence to a short paragraph. Must pass the filter (see below). |

### Entry types

**`observation`** — a genuinely new pattern not covered by anything in the current model. Use this when you've noticed something that a fresh agent tomorrow would work differently knowing.

```jsonl
{"ts": "2026-05-01T20:00:00Z", "session": "myvault-inbox", "project": "myvault", "type": "observation", "pattern_ref": null, "text": "Strongly prefers concrete examples over abstract descriptions — asked for examples 3 times in one session."}
```

**`confirmation`** — an existing pattern held in a meaningfully different context. Not every confirmation is worth logging; only log when the new context adds signal (a new project type, a higher-stakes situation, etc.).

```jsonl
{"ts": "2026-05-03T18:00:00Z", "session": "norn-refactor", "project": "norn", "type": "confirmation", "pattern_ref": "concrete-examples", "text": "Examples preference confirmed in a refactoring context — asked for a before/after example rather than a description of the change."}
```

**`correction`** — the model is wrong or incomplete. Highest-value type. Write corrections whenever this session contradicted what the model says.

```jsonl
{"ts": "2026-05-05T21:00:00Z", "session": "brain-kit-docs", "project": "brain-kit", "type": "correction", "pattern_ref": "prefers-brevity", "text": "Model says prefers terse output, but for reference docs requested more detail and examples. Context-dependent: brevity for task output, depth for documentation."}
```

**`calibration`** — something that caused friction that the model could have prevented. Bug reports against the model's predictions.

```jsonl
{"ts": "2026-05-07T19:00:00Z", "session": "myvault-brainstorm", "project": "myvault", "type": "calibration", "pattern_ref": null, "text": "Jumped into implementation before discussion — user had to redirect. Model should flag that brainstorming sessions need discussion-first, not code-first."}
```

## Seed entry convention

The bootstrap subcommand seeds the log with initial entries from an interview or a persona file. Seed entries are prefixed in the session field to distinguish them from observed entries:

- `[seed-from-interview]` — seeded via the 5-question bootstrap interview
- `[seed-from-persona]` — seeded from a hand-authored persona file

```jsonl
{"ts": "2026-01-15T10:00:00Z", "session": "[seed-from-interview]", "project": "bootstrap", "type": "observation", "pattern_ref": null, "text": "Works primarily in TypeScript and Go. Prefers functional patterns where the language supports them."}
```

Seed entries are downgraded during consolidation once real observed entries cover the same ground. After 5+ real sessions, seed entries that remain unchallenged are either promoted to canonical patterns or dropped.

## Consolidated model structure

The consolidated model is a markdown file generated by `/partner-model consolidate`. It is organized into themed sections, each containing pattern bullets.

### Themes

Common themes (consolidation may add new ones if 2+ entries support them):

- **Design Thinking** — how the user approaches problems
- **Communication** — comms style, signals, tells
- **Working With Agents** — preferences for spec, autonomy, when to intervene
- **Quality** — standards, review behavior, regression tolerance
- **UX Sensibility** — taste, iteration patterns
- **Technical Profile** — stack, tools, expertise depth
- **Agent Calibration** — concrete corrections and lessons

### Pattern bullets

Each pattern is a bullet under its theme section. The format:

```markdown
## Communication

- **Prefers concrete examples.** Asks for examples over abstract descriptions, especially when evaluating design options. (confirmed: norn-refactor, myvault-inbox)
- **Terse answers signal flow state.** Short replies during brainstorming mean "keep going" not "I'm disengaged."
  - Why: Distinguishing flow-state terseness from confusion prevents unnecessary interruptions.
```

A `Why` annotation is added when the reasoning isn't obvious — it helps a fresh agent apply the pattern correctly.

Corrections are cited: `(corrected 2026-05-05 — context-dependent, not universal)`.

## Profile semantics

The `partner_model.profile` key in `.vault.toml` selects which consolidated model file is used. This lets one vault maintain separate models per context:

| Profile | Model filename |
|---|---|
| `default` (or unset) | `partner_model.md` |
| `work` | `partner_model.work.md` |
| `personal` | `partner_model.personal.md` |

Paths are relative to the vault root and resolved using the `partner_model.path` config value as the base (with the profile suffix inserted before `.md`).

In v0.1, **all profiles share the same JSONL log** (`partner_model_log.jsonl`). Profile-scoped logs are deferred to v0.2.

## The lifecycle

```
bootstrap  →  log observations  →  consolidate  →  refine
   ↑                                                   |
   └──────────────── (repeat every few sessions) ──────┘
```

1. **Bootstrap:** Seed the log with initial entries via interview or persona file.
2. **Observe:** Each session end, the partner-model skill appends focused entries to the log.
3. **Consolidate:** Run `/partner-model consolidate` monthly or after a significant accumulation of new observations. It rewrites the model from the log.
4. **Refine:** The model improves over time as corrections challenge prior entries and confirmations strengthen patterns.

---

## Rules

**Do not edit the consolidated model directly.** It is generated output — the next consolidation will overwrite your changes. If you need to change a pattern, write a `correction` log entry describing the change, then run consolidation.

**The log is append-only.** Never delete or modify existing log entries. The log is the audit trail; the model is the derived view.

**Do not read the log before writing entries.** Observations should be pure and unbiased. Deduplication and conflict resolution are consolidation's job.

**Preserve `document_id` in the consolidated model.** If an external indexer has assigned a `document_id` frontmatter field to the model file, it must survive consolidation rewrites verbatim. See [strict-mode-ontology.md](strict-mode-ontology.md) for details on reserved frontmatter.
