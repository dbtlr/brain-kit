# Strict mode ontology

Strict mode (`mode.strict = true` in `.vault.toml`) enforces a typed-note ontology derived from a markdown vault system. The goal is typed-note-compatible structure: consistent frontmatter that enables cross-tool semantic search and entity resolution by external indexers.

In brain-kit v0.1, strict mode installs the ontology via templates and validates workspace notes. It does not enforce every type/kind value at write time — it documents the vocabulary so your notes are compatible with the full structured-vault toolchain.

Enable strict mode if you want structured-vault parity. Use minimal mode for a lighter-weight setup. See [vault-config.md](vault-config.md) for the config key.

---

## The three structural types

Every typed note declares its structural type via the `type:` frontmatter field.

| `type:` | What it is |
|---|---|
| `note` | Persistent canonical content. Prose-first. Gets a `kind:` that classifies what kind of note it is. |
| `task` | Actionable work item. Has a status lifecycle. No `kind:` — tasks have no variants. Uses `workspace:` and `status:` instead. |
| `agent-artifact` | AI-generated execution material (plans, specs, reviews, logs, summaries). Uses `artifact_kind:`, not `kind:`. |

Notes use `kind:` to express what they are. Tasks and agent-artifacts do not.

## `kind:` groups for notes

`kind:` classifies a `type: note` into one of four groups. The group determines what additional fields are expected and how the note is handled by indexers.

### Entity kinds

Entity notes declare a named entity. Indexers resolve these as reusable references throughout the vault.

| `kind:` | What it represents |
|---|---|
| `workspace` | A project or work context. The canonical workspace note (`my-project.md`). |
| `domain` | A knowledge domain or area of concern (e.g., Technology, Finance). |
| `persona` | A self-description note or role-based context. |
| `person` | A named individual (colleague, stakeholder, contact). |
| `technology` | A technology, tool, platform, or library. |

Entity notes require the **entity declaration fields**:
- `title:` — human-readable display name
- `aliases:` — list of alternate names the indexer should resolve
- `description:` — one-line summary

```yaml
---
type: note
kind: workspace
title: Brain Kit
aliases:
  - brain-kit
description: Claude Code plugin for personal AI infrastructure.
created: 2026-01-15T09:00
modified: 2026-05-10T14:30
---
```

**Do not strip or rewrite entity declaration fields.** The indexer uses `title`, `aliases`, and `description` verbatim. Modifying them breaks entity resolution.

### Structural kinds

Positional or transient notes with a time or event anchor.

| `kind:` | What it represents |
|---|---|
| `daily` | Daily journal entry. Lives in `Journal/YYYY/YYYY-MM-DD.md`. |
| `log` | Session dev log. Lives in `Log/`. Written by `/devlog write`. |
| `observation` | Standalone observation or note-to-self. |
| `meeting` | Meeting notes with attendees and date. |
| `report` | Generated or curated report (health check, summary, etc.). |

Structural kinds are not resolved as entities — they are transient by nature.

Log frontmatter example (written by `/devlog write`):

```yaml
---
type: note
kind: log
workspace: "[[brain-kit]]"
date: 2026-05-10
---
```

### Content kinds

The workhorse group. Durable knowledge notes that live in `notes/` or `Notes/`.

| `kind:` | What it's for |
|---|---|
| `research` | Findings from investigation. Reusable knowledge, not throwaway. |
| `decision` | A decision made, with context and rationale. |
| `learning` | Something discovered that's worth retaining. |
| `spec` | Technical specification. |
| `plan` | Approach or roadmap for work. |
| `user-story` | User-facing requirement in story form. |
| `brainstorm` | Open-ended exploration. Rough and evolving is fine. |
| `article` | Polished prose intended for external publication. |
| `idea` | Early-stage concept. May or may not be developed further. |

Content kinds validate against the base note schema. No extra required fields beyond `type` and `kind`.

```yaml
---
type: note
kind: decision
title: Use TOML for vault config
---
```

### System kinds

Infrastructure notes that live in `System/`. Not for regular vault content.

| `kind:` | What it's for |
|---|---|
| `template` | A frontmatter template for a typed note. |
| `model` | The partner model consolidated file. |
| `reference` | Reference documentation (like this file). |

## `artifact_kind:` for agent-artifacts

`type: agent-artifact` uses `artifact_kind:` instead of `kind:`. Valid values:

| `artifact_kind:` | What it is |
|---|---|
| `plan` | Implementation plan written by an agent. |
| `spec` | Technical spec written or generated by an agent. |
| `review` | Code review or PR review produced by an agent. |
| `log` | Execution log from an agent session. |
| `summary` | Summary of work, findings, or state. |

```yaml
---
type: agent-artifact
artifact_kind: plan
---
```

Agent artifacts live in `{workspace}/agent-artifacts/` and are not treated as canonical knowledge. Promote durable content to `notes/` by rewriting it as a `type: note` with an appropriate content kind.

## Reserved frontmatter: `document_id`

`document_id` is a UUID v4 assigned by external indexers (the Vault Memory pipeline in structured-vault). If your notes have this field, **do not create, modify, or remove it**. Skills preserve it verbatim across rewrites.

Templates should not include `document_id`. It is added by the indexer, never by hand.

## When to use strict vs minimal

**Use strict if:**
- You want structured-vault compatibility — cross-tool entity resolution, semantic search, Vault Memory indexing
- You're maintaining a vault long-term and want consistent structure
- You're sharing vault content with tools that expect typed notes

**Use minimal if:**
- You want a lightweight personal setup with low overhead
- You're experimenting or onboarding
- You don't need entity resolution or external tooling

You can initialize in minimal mode and migrate to strict later. Strict mode adds requirements but doesn't change the directory structure — see [workspace-contract.md](workspace-contract.md) for what strict adds to the workspace layout.
